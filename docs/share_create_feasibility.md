# 115「创建分享」能力: 现状盘点与可行性

> 创建时间: 2026-09-26
> 触发: 用户希望"在目录浏览/搜索里点击分享"

## 一句话结论

**目前 0 个创建分享的 API, 只能「消费」(snap + receive), 没法「发出」。**

## 当前 `api115.py` 里的分享相关函数

| 函数 | 作用 | 用途 |
|---|---|---|
| `share_snap(code, pw, cookie)` | 拆别人分享给我链接, 看里面有什么 | 转存前预览 |
| `share_receive(code, pw, fids, to_cid, cookie)` | 把别人分享的东西转存到我的目录 | 转存执行 |
| `share-copy` (前端) | 把已转存的 share_code + 访问码拼成可粘贴格式 | 仅文案包装, 不生成新链接 |

## 为什么不直接加

1. **115 公开 webapi 没有 "create share" 端点**。我搜了 115.com/open, github.com/115dev/openapi, yuque.com/115api/share, 全部 404。
2. **业内常见的私有端点** `/share`, `/files/share`, `/share/create` —— **没有任何官方文档**，参数经常变动，调用频繁会触发 WAF 并可能封号。
3. **浏览器/客户端的方式** —— 走 `/share.html` 内嵌加密参数 (u_key / x_sign / various sig), 需要 hook Chrome 客户端才能稳定拿到签名逻辑，工作量很大。

## 如果将来要做

有三条路，按推荐顺序：

### 路径 A (推荐): 仅前端入口, 手工跳转

```js
data-action="share-open-115"
  -> 弹一个小条：标题/链接/访问码已放到你剪贴板
  -> window.open(`https://115.com/?tab=share&cid=...`, "_blank")
  -> 用户在 115 网页里点 "创建分享", 复制回来
```

- **优点**：零风险, 零后端, 5 分钟搞定
- **缺点**：需要切到浏览器

### 路径 B: 抓包逆向私有端点

- 抓 115 Windows 客户端的 `/share` POST 请求
- 提取 u_key 加密逻辑（一般用 ECDH + 自家算法）
- 在 `api115.py` 里照实现一个 `share_create(fids, ...) -> {share_code, receive_code}`
- **优点**：UI 无缝, 一键搞定
- **风险**：参数随客户端版本变, 维护成本高; 触发风控/封号风险

### 路径 C: 仅对账已存在的 share_link

把"已经创建过的分享"按 cid 缓存到本地 `share_links.db`，
提供一个手动录入入口，让用户在 115 网页创完链接后回填。

- **优点**：完全合法, 没有抓包
- **缺点**：仍然需要切到浏览器, 仅做了"记一笔"

## 建议

如果未来真有这需求，**先走路径 A**，5 分钟实现跑通流程，等用户量起来再考虑 B。路径 C 是路径 A 的持久化升级版。
